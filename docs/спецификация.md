# tg-summary-bot — спецификация

Этот документ описывает замысел: что бот делает, как устроен и почему решения приняты
именно такие. Как поднять и обслуживать работающий экземпляр — в `README.md` в корне
репозитория.

## Назначение

Участникам активного чата некогда читать всю переписку. Бот раз в сутки публикует в чат
краткое изложение того, что в нём обсуждали с прошлого раза.

## Где работает

- Любой сервер с Docker и compose (проверено на Ubuntu 24.04).
- Python + aiogram, база — SQLite.
- Приём обновлений — **long polling**. Вебхук не подходит: сервер не должен принимать входящие от Telegram.
- Модель — через OpenRouter.
- Прокси **необязателен**, но задаётся одной настройкой сразу для Telegram и OpenRouter — на случай, когда прямой доступ к ним закрыт (например, OpenRouter не пускает запросы с российских адресов).

Разворачивается копированием папки на сервер и командой `docker compose up -d --build`.

## Данные

**Одна база, два входа.** Сообщения попадают в неё двумя путями:

1. **Живой поток** — бот принимает сообщения по поллингу и складывает.
2. **Импорт выгрузки** — разбор `result.json` из Telegram Desktop.

Дедупликация по паре «чат + номер сообщения»: выгрузки можно лить повторно, внахлёст и частями, база не испортится.

Саммари **всегда строится по базе**, а не по живому потоку. Поэтому тестовый прогон и боевой запуск — один и тот же код над одними данными.

**Берём только текст и подписи** к вложениям. Голосовые не расшифровываем, картинки не распознаём.

**Название чата** бот берёт из данных Telegram автоматически, для настроек оно не обязательно.

## Реакции-метки

Бот получает уведомления о реакциях и знает, **кто именно** поставил реакцию (поле `user`).
Владелец отмечает важные сообщения условленной реакцией — при суммаризации такие сообщения
подаются модели отдельным блоком «отмечено важным».

Условия работы:
- бот должен быть **администратором** чата (достаточно админа без единого права);
- при запуске бот явно запрашивает тип обновлений `message_reaction`;
- приходят только реакции, поставленные после подключения; за прошлое — никак.

## Логика ежедневного запуска

Бот работает непрерывно: держит long polling (запрос висит до 30 секунд, ответ приходит сразу при появлении сообщения). Раз в 5 минут срабатывает проверка расписания по всем настроенным чатам.

**Одно состояние на день.** У каждого чата есть `day_state` с датой — что с сегодняшним саммари:

| Состояние | Что делает тик после назначенного времени |
|---|---|
| `waiting` | сообщений меньше порога → ставит `skipped`. Хватает → делает саммари: получилось `done`, не получилось `failed` |
| `failed` | пробует снова, пока не получится `done`. Порог не перепроверяется |
| `skipped` | ничего, до завтра |
| `done` | ничего, до завтра |

Наступили новые сутки — состояние сбрасывается в `waiting`. Это единственный переход по времени.

Отсюда поведение, которое и требовалось: **в течение дня бот возвращается к чату только после технического сбоя**. Если утром сообщений не хватило, а к вечеру переписка разошлась — саммари в тот же день не выйдет, всё переносится на следующее назначенное время.

Состояние лежит в базе, поэтому перезапуск бота или падение сервера посреди дня ничего не ломают.

Саммари публикуется в тот же чат. Отметка `last_message_id` сдвигается на последнее вошедшее сообщение **только при успешной публикации в рабочем режиме**; `/test` её не трогает.

Период саммари плавающий: не «за сутки», а «с прошлого саммари».

При первой настройке чата саммари делается **по всему накопленному**. Если это не нужно — отметка правится прямым редактированием базы.

Время — по Москве, зашито в коде.

## Длина и разметка саммари

Длину держит промпт: в нём задаётся целевой размер (порядка 2000 знаков). Саммари, которое не читается за минуту, бессмысленно — тот, кому некогда читать чат, не станет читать и его пересказ.

**Модель возвращает простой текст с минимальными служебными метками** — `##` в начале строки для заголовка темы и `[[id]]` для места ссылки на обсуждение. HTML собирает бот на постобработке (экранирование, `<b>`, ссылки, `parse_mode=HTML`). Так модель не может выдать разметку, которую Telegram отклонит. Подробности — в `требования_к_данным.md`, раздел «Обработка ответа модели перед публикацией».

Лимит сообщения Telegram — 4096 знаков. Чтобы в него заведомо уложиться, ответ модели длиннее 4000 знаков жёстко обрезается ещё до наложения разметки, и в лог пишется, что саммари обрезано. Это сигнал доработать промпт или сменить модель, на части не разбиваем.

## Логи и сбои

Лог — `data/bot.log` рядом с базой. Пишутся **только события**: публикация, ошибка, пропуск дня по недобору, импорт выгрузки, тестовый прогон. Тики без событий не логируются.

Ротация по размеру: файл пишется до 10 МБ, затем переименовывается в `bot.log.1` и начинается новый. Хранится три старых копии, самая древняя удаляется.

Уведомлений владельцу при сбое **не шлём**. Диагностика — лог плюс `last_error` в `/status` рядом с состоянием `failed`.

Повторные попытки после сбоя идут каждые 5 минут до полуночи. Ошибочные запросы к модели не тарифицируются.

## Команды

Только в личке и только владельцу (`OWNER_ID`).

| Команда | Действие |
|---|---|
| `/test [количество] [id чата]` | тестовое саммари по последним N сообщениям. По умолчанию 30 сообщений и чат из `default_chat`. Отметку не двигает |
| `/status` | состояние: чаты, накопление, отметки, следующий запуск, ошибки |

Если чат не указан и `default_chat` не задан — бот отвечает «чат по умолчанию не задан, укажите id чата».

**Импорт выгрузки — не команда:** владелец отправляет боту файл `result.json`, бот разбирает и отвечает отчётом (какой чат, за какой период, сколько добавлено новых, сколько уже было). Ограничение облачного Bot API — **20 МБ**; крупные выгрузки режем в Telegram Desktop по периодам и присылаем частями.

К каждому тестовому ответу — служебная строка: сколько сообщений вошло, модель, время, стоимость.

Команд внутри чата нет.

### Пример вывода `/status`

```
Чаты с настройками
• Сообщество — id -1001234567890
  накопилось 47 сообщений (порог 30)
  последнее саммари 21.07 09:00, по сообщение 15423
  сегодня: waiting, запуск в 09:00

Без настроек
• Тестовый чат — id -1009876543210
  12 сообщений в базе, саммари не делается

Чат по умолчанию: Сообщество
```

Состояния показываются как есть: `waiting`, `skipped`, `done`, `failed`. При `failed` рядом печатается текст последней ошибки.

## Настройки

**Чат в базе и чат в настройках — разные вещи.** Бот пишет в базу всё, что видит.
Присутствие чата в `chats` означает «суммаризировать»; чата нет — сообщения копятся, но ничего не публикуется.
Ненастроенные чаты видны в `/status` с пометкой, что саммари не делается.

Порядок: сначала добавили бота в чат, потом настроили.

### `config/chats.yaml`

```yaml
default_chat: -1001234567890

chats:
  -1001234567890:
    name: Сообщество
    prompt: default
    min_messages: 30
    time: "09:00"
    mark:
      reaction: "🔥"
      by: [123456789]
```

- Все поля внутри чата необязательны; значения по умолчанию (30 сообщений, 09:00) — в коде.
- `prompt` — имя файла из `prompts/` без расширения. Имена файлов латиницей.
- `mark.reaction` — сам символ эмодзи. Telegram разрешает ограниченный набор эмодзи для реакций; кастомные премиум-реакции не поддерживаем.
- `mark.by` — чьи реакции считать метками.
- Настройки перечитываются перед каждым запуском, отдельной команды перезагрузки нет.

### `.env`

```
TELEGRAM_TOKEN=      токен бота
OWNER_ID=            id владельца — только ему бот отвечает в личке
OPENROUTER_KEY=      ключ OpenRouter
MODEL=               модель
PROXY=               один прокси и для Telegram, и для OpenRouter
```

`.env` не монтируется в контейнер: его читает `docker compose` на хосте при запуске.
Поэтому после правки `.env` нужен `docker compose up -d`, иначе контейнер работает со старыми значениями.

## Раскладка на сервере

```
/opt/tg-summary-bot/
  prompts/            промпты, файлы .md
  config/chats.yaml   настройки чатов
  data/bot.db         база
  .env                секреты
  docker-compose.yml
```

`prompts/`, `config/`, `data/` — тома: лежат на диске сервера, пересборка и перезапуск их не трогают.
Код живёт внутри образа и обновляется пересборкой.

Промпты бот читает с диска **на каждом прогоне** — правка промпта действует сразу, без перезапуска.

## База данных

SQLite, файл `data/bot.db`. Пять таблиц.

**`messages`** — сообщения:
`chat_id`, `message_id`, `date`, `user_id`, `user_name`, `text`, `reply_to`
Ключ — пара `chat_id + message_id`; она же отсекает дубли при повторной заливке выгрузок.

**`chats`** — что бот видел:
`chat_id`, `title`, `first_seen`
Название приходит от Telegram, обновляется при переименовании чата.

**`reactions`** — реакции:
`chat_id`, `message_id`, `user_id`, `emoji`
Строка на реакцию, при снятии удаляется. Метки для саммари отбираются отсюда по `mark` из настроек.

**`summary_state`** — до какого места просуммировано и что с сегодняшним саммари:
`chat_id`, `last_message_id`, `day`, `day_state`, `last_error`
Одна строка на чат, правится вручную при необходимости. `day_state` — одно из `waiting`, `skipped`, `done`, `failed`.

**`summaries`** — опубликованные саммари:
`chat_id`, `created_at`, `from_message_id`, `to_message_id`, `model`, `prompt`, `text`, `cost`
Только рабочие публикации; тестовые прогоны не сохраняются. `prompt` — имя файла. `cost` берётся из ответа OpenRouter (поле `usage.cost` приходит в каждом ответе, включать ничего не нужно).

**Создание и изменение.** При старте бот выполняет `CREATE TABLE IF NOT EXISTS` — файл базы SQLite создаёт сам, отдельного шага установки нет. Автоматических миграций нет: изменения схемы применяются вручную, отдельными SQL-запросами к базе.

**Решения по хранению:**
- сообщение отредактировали — текст перезаписывается, история правок не хранится;
- сообщения хранятся бессрочно (сто тысяч сообщений — порядка 20 МБ);
- свои публикации бот обратно не получает, поэтому в `messages` они не попадают и повторно не суммаризируются.

## Ограничения Telegram, которые нельзя обойти

- Бот не видит историю чата до своего добавления — только выгрузка.
- Бот **никогда** не видит сообщения других ботов.
- Реакции — только при правах администратора и только за период после подключения.
- Скачивание присланных файлов — до 20 МБ.
- Чтобы бот видел все сообщения группы, у него должен быть **отключён режим приватности** (`/setprivacy` у @BotFather).

## Охват

Один экземпляр бота обслуживает произвольное число чатов: добавление чата — правка
`config/chats.yaml`, менять код не нужно. Рассчитано на обычные группы, без тем.
